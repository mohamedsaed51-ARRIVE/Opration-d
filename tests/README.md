# اختبارات ARRIVE Operations Dashboard

## التشغيل

```bash
node tests/run_all.js            # كل الاختبارات، من مجلد المشروع ثم من جذر النظام
node tests/run_all.js --verbose  # مع تفاصيل كل اختبار
node tests/test_kpi_baseline.js  # ملف واحد
```

- **المتطلبات:** Node.js فقط، والاختبارات جُرّبت على v22. لا تحتاج `npm install` ولا اتصالًا بالشبكة ولا وصولًا إلى Google.
- **ملفات الإنتاج (`Code.gs` و `index.html`) لا تُعدَّل** أثناء الاختبار، وتُقرأ فقط.

## كيف تعمل

| الملف | الوظيفة |
|---|---|
| `helpers/loadBackend.js` | يحمّل `Code.gs` **كاملًا** داخل بيئة `vm` معزولة. خدمات Google تُستبدل ببدائل تعمل في الذاكرة. لا يوجد `fetch` ولا `require` ولا `process` داخل البيئة، و`UrlFetchApp` يرفع خطأ إذا استُدعي |
| `helpers/loadFrontend.js` | يستخرج دوال محددة بالاسم من `index.html` الحقيقي كما هي حرفيًا، ويشغّلها معزولة. الصفحة كاملة لا يمكن تحميلها لأنها تحتاج متصفحًا وشبكة. إذا لم يوجد الاسم مرة واحدة بالضبط، يتوقف برسالة خطأ ولا يخمّن |
| `helpers/harness.js` | أداة اختبار بسيطة. تحجب الشبكة في عملية الاختبار كلها، وتثبّت المنطقة الزمنية على `Africa/Cairo` |
| `fixtures/fakeShipments.js` | بيانات **وهمية** بالكامل: البوالص `TEST-…` والأسماء كلها «تجريبي» |

## معنى علامة «baseline — needs business-rule approval»

الاختبار الذي يحمل هذه العلامة يثبّت **سلوك الكود الحالي** فقط، **ولا يعني أن السلوك صحيح أو معتمد**. إذا اعتمدت الإدارة تعريفًا مختلفًا، يُحدَّث الاختبار مع تعديل الكود في نفس التغيير، وفشله حينها هو الإشارة المقصودة.

## قائمة الاختبارات

### `test_loader.js`: سلامة بيئة الاختبار

| # | ما يختبره | النتيجة المتوقعة |
|---|---|---|
| L1 | تحميل `Code.gs` كاملًا | كل دالة معرّفة على المستوى الأعلى متاحة |
| L2 | الاستقلال عن مجلد التشغيل | التحميل ينجح عند التشغيل من `/` |
| L3 | عدم الاعتماد على `/tmp` | لا يوجد ملف اختبار يشير إليه |
| L4 | عزل الشبكة | لا `fetch` ولا `require` ولا `process`، و`UrlFetchApp` و`https.request` يرفعان خطأ |
| L5 | خلوّ البيانات والملفات من بيانات إنتاج | بيانات الاختبار وهمية، ولا يوجد رابط Web App أو Google Docs |
| L6 | الاستخراج من `index.html` حرفي | النص المستخرج موجود كما هو في الملف ويعمل |
| L7 | رفض الأسماء غير الموجودة | يرفع الخطأ «expected exactly 1» |

### `test_kpi_baseline.js`: مؤشرات الخلفية كما هي اليوم

| # | ما يختبره | النتيجة وفق الكود الحالي | يحتاج اعتمادًا |

| K2 | حذف التكرار | يُحتفظ بالسجل صاحب أحدث تاريخ آخر حالة، وعند التساوي بالصف الأخير | ✅ (قاعدة التساوي) |
| K3 | إجمالي الشحنات | البوالص الفريدة داخل الشهر، وتُستبعد الصفوف بلا رقم بوليصة | ✅ |
| K4 | نسبة التسليم | المسلّم ÷ الإجمالي | ✅ |
| K5 | نسبة المرتجع | المرتجع ÷ (الإجمالي − قيد التشغيل) | ✅ |
| K6 | نسبة رفض الاستلام | الرفض ÷ (الإجمالي − قيد التشغيل) | ✅ |
| K7 | نسبة النجاح | (المسلّم + الرفض) ÷ الإجمالي | ✅ |
| K8 | الحالات غير المصنفة | تُعدّ وتُعرض ولا تُحذف | — |
| K9 | SLA على بيانات الشهر كاملة | المسلّم فقط، بالأيام الكسرية، والقيمة ≤ 2 «ملتزم» | ✅ |
| K10 | الحالات الحدية للـ SLA | 2.0 ملتزم، و2.0 + دقيقة مخالف، والتاريخ الفارغ مستبعد | ✅ |
| K11 | المتوسط والوسيط والحد الأقصى | الوسيط = الوسيط الأعلى عند العدد الزوجي | ✅ |
| K12 | فئة المحاولة (الخلفية) | بالأيام الكسرية | ✅ |
| K13 | اكتشاف الأعمدة بالمطابقة الجزئية | «تاريخ التسليم المتوقع» يُلتقط على أنه تاريخ التسليم | ✅ (خطر) |

| C6 | اختلاف معروف: الشهر الواحد مقابل «كل الشهور» | التكرار بين الأشهر يُحسب مرتين، ومقام نسبة الرفض على مستوى الفرع مختلف | ✅ |

### `test_sla_invalidation_bug.js`: إعادة البناء المرحلي بعد تغيير SLA

يشغّل `buildNextSummaryBatch` الحقيقية، مع ساعة وهمية وبناء وهمي للأشهر. يتحقق من:
- أن الإكمال لا يُعلَن قبل إعادة بناء كل الأشهر بالإعداد الجديد.
- أن الاستئناف يبدأ من نوفمبر.
